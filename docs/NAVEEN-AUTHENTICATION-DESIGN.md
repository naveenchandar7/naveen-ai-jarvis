# NAVEEN AI Authentication Design

## Status

This document defines the authentication boundary for the locked NAVEEN hybrid architecture. It intentionally does **not** implement Rust↔Python transport, Python Core, STT, LLM, MCP, or tool execution.

## 1. Security model

NAVEEN has two independent identities:

- **Human user identity:** future host-owned local unlock/authentication. This is separate from Core authentication and is not implemented by this milestone.
- **Python Core identity:** the Rust/Tauri host authenticates the specific Core process it launched for the current application launch.

Authentication proves identity. Authorization decides whether an already authenticated principal may perform a capability. These are separate operations.

React/Three.js is never an authentication authority and never receives authentication secrets.

## 2. Core authentication mechanism

The proposed mechanism is a **per-launch, in-memory 256-bit shared secret** generated by Rust, plus a cryptographic challenge/response handshake using HMAC-SHA-256.

Rust is the trust anchor because it launches/supervises Python. The launch secret is generated when the host starts, lives only in host memory, and is destroyed with the host. It is never written to disk, source, logs, command-line arguments, or frontend state.

The initial target is Windows. Windows CNG (`bcrypt.dll`) is used for cryptographically secure random bytes and HMAC-SHA-256. Microsoft recommends the system-preferred RNG via `BCryptGenRandom` with `BCRYPT_USE_SYSTEM_PREFERRED_RNG` for cryptographic randomness.

### Secret bootstrap

The authentication library deliberately does not implement transport. At the transport milestone, Rust should give the launched Python process the launch secret through a **private OS-protected bootstrap channel** rather than command-line arguments or ordinary environment variables.

The preferred shape is an OS-protected local channel associated with the launched child. A Windows named pipe is acceptable for the actual IPC layer only when its security descriptor restricts access to the intended local logon context; a private inherited handle/anonymous pipe may be used for one-time secret bootstrap. The authentication protocol remains independent of that choice.

## 3. Handshake

```text
Rust host                              Python Core
    |                                      |
    | -- launch secret (future OS-       |
    |    protected bootstrap, once) ----> |
    |                                      |
    | -- Challenge ----------------------> |
    |    version                          |
    |    launch_id                        |
    |    challenge_id                     |
    |    32-byte nonce                    |
    |    issued_at / expires_at           |
    |    expected client_id               |
    |    correlation_id                   |
    |                                      |
    | <--------- ChallengeResponse ------- |
    |              same version           |
    |              launch_id              |
    |              challenge_id           |
    |              client_id              |
    |              correlation_id         |
    |              HMAC-SHA-256(proof)    |
    |                                      |
    | -- Authenticated session ---------- |
    |    session_id                       |
    |    expiry                            |
    |                                      |
```

The proof covers a canonical transcript containing protocol version, launch identity, challenge identity, challenge nonce, timestamps, expected client identity, and correlation identifier. This prevents an attacker from replaying a proof for a different launch/challenge/context.

## 4. Session establishment

A successful challenge response causes Rust to create an in-memory authenticated session containing:

- randomly generated 128-bit session ID;
- per-session 256-bit session key derived from the launch secret and handshake transcript;
- issuance and expiry timestamps;
- revocation state;
- last accepted message sequence number.

The **session ID is an identifier only**. It is never accepted as proof of authentication.

The session key is not serialized into logs or exposed to React. Python derives the same session key from the launch secret and the exact handshake transcript during its future client implementation.

## 5. Session lifetime and invalidation

Provisional defaults implemented by this milestone:

- challenge lifetime: **30 seconds**;
- authenticated Core session lifetime: **10 minutes**;
- challenge is single-use after successful authentication;
- explicit invalidation revokes the session immediately;
- host shutdown invalidates all sessions implicitly by destroying in-memory state;
- a session from a previous host launch is unusable by a fresh host instance because the previous session registry and launch identity no longer exist.

These TTL values are implementation defaults, not permanent architecture decisions.

## 6. Replay protection

### Handshake replay

Each challenge has a unique random ID and nonce. A challenge can be successfully consumed only once. Responses for consumed challenges are rejected as replayed.

### Session-message replay

The authentication boundary accepts an explicit sequence number for future messages. The MAC covers:

```text
protocol_version
session_id
correlation_id
sequence_number
message_digest
```

Only strictly increasing sequence numbers are accepted. Reusing or going backwards in sequence is rejected. The future transport layer must bind `message_digest` to the exact canonical bytes of the authenticated IPC message.

## 7. Authorization boundary

The Security Gateway receives a host-issued `AuthenticatedSession`, not a caller-constructed session ID.

Authorization then evaluates host-owned capability policy:

```text
Authenticated principal
        ↓
Capability ID lookup
        ↓
Host-owned permissions + risk
        ↓
Deny by default
        ↓
Optional explicit confirmation
```

The caller never supplies its own effective permission set or risk level.

## 8. Audit events

Authentication failures and state changes produce **sanitized in-memory audit events**. Events may include timestamps, correlation IDs, session IDs, and a coarse failure reason.

They must never contain:

- launch secret;
- session key;
- challenge nonce;
- authentication proof/MAC;
- raw message contents;
- passwords or API keys.

A later host logger may serialize these sanitized events, but secrets must remain outside logs.

## 9. Failure handling

Failures are fail-closed. The boundary distinguishes protocol, malformed-input, identity, replay, expiry, revocation, and cryptographic failures internally. A future transport may collapse these to a smaller external error vocabulary to avoid unnecessary information disclosure.

No authentication failure is allowed to establish a session.

## 10. Threat model

| Threat | Mitigation |
| --- | --- |
| React/webview tries to impersonate Core | React has no Core secret and no direct Rust↔Python channel |
| Python process is replaced/impersonated | Rust authenticates the launched Core using a per-launch secret and challenge/response |
| Stolen previous-launch session ID | Session registry is in-memory and launch-bound; ID alone is never sufficient |
| Replay of a valid handshake | One-time challenge ID + nonce + expiry + consumed-state |
| Replay of a valid session message | MAC + strictly increasing sequence number |
| Stale/expired session | Explicit expiry and revocation checks |
| Caller supplies fake permissions/risk | Capability policy is host-owned; request carries only capability ID |
| Secrets leaked to frontend | Auth state and keys live only in Rust/auth boundary |
| Secrets leaked to Git/logs | No persistent secret material; audit events are sanitized |
| Local same-user process attempts IPC | Future local IPC must use OS ACLs plus this cryptographic authentication |
| Malicious Core/prompt injection attempts privileged action | Core can request capabilities only; Security Gateway remains authoritative |
| Network exposure | No TCP listener is part of this design; IPC is local and OS-protected |

## 11. Open decisions after this milestone

### User authentication

The **human-user authentication mechanism remains open**. The architecture should expose a host-owned `UserAuthenticator` interface and prefer platform-backed local authentication (for Windows, an OS-integrated credential/Windows Hello style provider can be evaluated) without making the rest of NAVEEN depend on it.

User authentication must never be reused as a substitute for Core authentication.

### Core bootstrap transport

Still open: private inherited handle/bootstrap pipe versus a hardened local named-pipe arrangement for the actual Rust↔Python channel. The chosen transport must remain local, authenticated, versioned, and least-privilege.

### Wire encoding

Still open. The authentication contract intentionally uses typed binary fields and does not lock JSON, protobuf, MessagePack, or another serialization format.

### Key lifecycle policy

The TTLs and re-authentication cadence can be tuned after real Core startup/shutdown behavior and failure-mode testing.

## 12. Explicit non-goals of this milestone

- no Rust↔Python transport;
- no Python process launch/supervision implementation;
- no STT/VAD;
- no LLM/provider/model;
- no MCP;
- no capability execution;
- no browser/shell/filesystem tools;
- no user credential database;
- no cloud authentication service.
